Complete 50-item evidence ledger

Every original finding, reconciled to current evidence

Open any item for its current status and remaining proof. The original diagnosis and proposed repair are retained beneath it for historical context.

CriticalThe planned Render deployment cannot connect to PostgreSQL

Original findingThe app asks Render for a PostgreSQL database, but the Python package that speaks to PostgreSQL is missing. Production startup fails before the website can serve a page.

Original repair directionAdd and pin the correct PostgreSQL driver, create a production-like smoke test, and prove the app boots against PostgreSQL before touching deployment.

CriticalA booking can charge the learner twice

Original findingThe booking route subtracted credits directly, then called another function that subtracted the same amount again. In the original audit, a two-credit booking took four credits.

Original repair directionCreate one authoritative ledger function that changes the balance exactly once and records the matching transaction in the same database operation.

CriticalCancellation and timeout refunds are incorrect

Original findingPending sessions can be refunded twice. Accepted sessions can receive no refund at all. The result depends on the session state instead of a clear cancellation policy.

Original repair directionDefine the policy, attach each hold and refund to a session ID, and enforce at most one refund per session at the database level.

CriticalA teacher may not be paid for a second session of the same skill

Original findingThe duplicate-payment check does not identify the actual session. Two valid sessions between the same people for the same skill look like one payment.

Original repair directionAdd a unique session ID to every payout and enforce one payout per completed session—not one payout per teacher, learner, and skill name.

CriticalTwo simultaneous actions can corrupt session or request state

Original findingTwo teachers can attempt to claim one request, or both participants can complete a session at nearly the same time. Current locking does not protect the whole business operation.

Original repair directionLock the request/session and both affected accounts, add uniqueness constraints, then test real simultaneous requests on PostgreSQL.

CriticalStudent verification can be completely bypassed

Original findingThe signup check only looks for text ending in .edu. It does not confirm that the text is a real address, and unverified accounts can still onboard, browse, book, and earn credits.

Original repair directionValidate the address properly, send a real email, and block every protected product action until verification succeeds.

CriticalFake accounts can farm referral credits

Original findingReferral credits are granted immediately, before the new account proves it belongs to a real student. An attacker can create many fake-looking accounts and inflate balances.

Original repair directionDelay rewards until verification and onboarding are complete, add abuse limits, and make referral rewards idempotent.

CriticalA proof-video URL can become a stored script attack

Original findingThe server accepted a javascript: link because the text also contained “youtube.com.” That link is saved and shown on public profiles.

Original repair directionParse the URL, allow only HTTPS, allow only exact approved video hosts, reject everything else, and add security regression tests.

CriticalBonus-credit endpoints can be repeated without limit

Original findingUpdating a proof link keeps awarding credits. Calling the ambassador route repeatedly keeps awarding two more. The interface hides the button, but an attacker does not need to use the interface.

Original repair directionDisable both reward programs for the trial, then later add one-time database constraints, approval state, audit logs, and abuse monitoring.

CriticalAny user can make themselves an ambassador and gain admin-like power

Original findingAmbassador status is instant and self-service. Ambassadors can run the global timeout operation that modifies other students’ sessions.

Original repair directionCreate separate user, ambassador, moderator, and administrator roles. Only a real background job or administrator should perform global maintenance.

CriticalThe skill-request board crashes with a 500 error

Original findingThe route tries to open a page file that does not exist. The monetization routes also reference missing pages.

Original repair directionEither finish the request-board journey and its tests or remove it from the trial. Keep monetization disabled and remove dead routes until they are real.

CriticalAccepted sessions receive a fake Google Meet link

Original findingThe app invents a URL that looks like Google Meet but does not create an actual meeting. Students will click it and fail to join.

Original repair directionFor the trial, let the teacher supply a validated meeting link or choose an approved public campus location. Add calendar integration only after the core trial works.

CriticalVerification and password-reset email are not production-ready

Original findingThe email library is missing, Render has no email configuration, and delivery errors are swallowed. A student can be told “sent” even though nothing was delivered.

Original repair directionAdd an approved transactional-email provider, verified sender, delivery monitoring, retries, and staging tests using real inboxes.

CriticalSecret reset links leak into logs and can use an attacker-controlled domain

Original findingEmail bodies—including verification and reset tokens—are printed. The domain in generated links comes from the incoming request, so a malicious Host header produced an evil-domain reset link during testing.

Original repair directionNever log email bodies or tokens, configure a canonical public URL, validate trusted hosts, and test link generation behind the real proxy.

CriticalThere is no safe database migration system

Original findingcreate_all() can create missing tables, but it does not safely upgrade existing tables. New fields can make a deployment crash against an older database.

Original repair directionAdd Alembic/Flask-Migrate, create reviewed forward and rollback migrations, and rehearse them on representative production-like data.

HighThe advertised account lockout does not work

Original findingFailed login attempts are never added to the counter. Five wrong passwords left the counter at zero in testing.

Original repair directionImplement account-aware throttling, increment and reset rules, secure lockout timing, and tests that prevent both brute force and denial-of-service abuse.

HighRate limiting is both unreliable and likely too restrictive

Original findingLimits are held in each web worker’s memory, so workers disagree. A low global limit can also block many students who share campus networking or a reverse proxy.

Original repair directionUse shared Redis storage, configure proxy IP handling safely, and set different limits for login, verification, browsing, static files, and money-moving actions.

HighThe six-digit student-verification code is weakly protected

Original findingIt uses a non-security random generator, has no enforced expiration, no retry limit, and no resend cooldown.

Original repair directionGenerate codes securely, store only a hash, expire them quickly, limit attempts, throttle resends, and alert on abuse.

HighThirty-day login sessions cannot be centrally revoked

Original findingA stolen signed cookie can remain useful, and resetting a password does not sign other devices out.

Original repair directionAdd session-version or server-side session controls, revoke sessions after password resets, and use a shorter sensible lifetime for shared student devices.

HighThe Content Security Policy is internally contradictory

Original findingIt blocks the external animation libraries and map images the page tries to load, but permits inline scripts—the category that needs tighter control.

Original repair directionRemove unused third-party scripts, self-host what remains, use nonces or hashes for necessary inline code, and allow only the exact map hosts if the map stays.

HighA requested session can be completed before the teacher accepts it

Original findingThe completion endpoint accepts both “requested” and “confirmed” states. Direct requests can bypass the intended journey.

Original repair directionDefine a strict state machine: requested → accepted → completed or cancelled/disputed. Reject every illegal transition server-side.

HighScheduling is incomplete and ambiguous

Original findingThe server can accept missing, invalid, or past dates. Timezones are not recorded, and the teacher does not see the requested date before accepting.

Original repair directionStore timezone-aware dates, validate an allowed range, show the exact time to both parties, and require acceptance of the schedule.

HighThere is no working report, block, dispute, or moderation flow

Original findingThe database has reputation counters, but students cannot report harm, block contact, dispute a session, or request a safety review.

Original repair directionBuild reporting and blocking first, then a moderator queue, evidence notes, resolution outcomes, credit reversals, and an immutable audit trail.

HighUnsafe or prohibited skills are only banned in policy text

Original findingA user can still list medical, clinical, weapons-related, illegal, or dangerously physical instruction because listing creation has no policy enforcement.

Original repair directionDefine permitted trial categories, block high-risk topics in code, add human review for flagged listings, and launch with one low-risk vertical.

HighUsers never affirmatively accept the terms, age rule, or safety waiver

Original findingThe terms say users must be 18 and accept a waiver, but signup records no checkbox, version, date, or proof of acceptance.

Original repair directionHave counsel review the documents, then record explicit versioned consent for terms, privacy, code of conduct, age eligibility, and safety rules.

HighThe privacy policy promises controls the product does not provide

Original findingThe policy promises access, correction, and deletion within 30 days, but there is no account-deletion or export workflow and no documented operator process.

Original repair directionBuild or document a reliable request process, define retention by data type, test deletion, and update the policy so every sentence matches reality.

HighAnonymous visitors can view student profiles

Original findingNames, schools, majors, skills, learning interests, reviews, and proof links can be visible without joining—even though Relay presents itself as a student-only community.

Original repair directionDecide the privacy model explicitly. For a trial, I would require verified login for full profiles and show only limited marketplace previews publicly.

HighThere is no real administrator or safety-operator system

Original findingThere is no safe way to suspend a user, remove harmful content, reverse credits, inspect a dispute, or prove who took an administrative action.

Original repair directionAdd least-privilege roles, protected admin tools, mandatory reasons, and an append-only audit log.

HighThe database does not enforce important business rules

Original findingBalances can lack exactness because they use floats. The database does not guarantee nonnegative balances, unique reviews, valid ratings, sensible prices, or different teacher and learner IDs.

Original repair directionUse integer credits or exact decimals and add database constraints so bad states are impossible even if application code has a bug.

HighCore web dependencies are behind current security fixes

Original findingThe pinned Flask version is covered by two low-severity advisories. The Werkzeug version has Windows-specific denial-of-service advisories. Render runs Linux, so the Werkzeug exposure is limited, but the stack is still stale.

Original repair directionUpgrade Flask and Werkzeug to fixed releases, review release notes, rerun all security and session tests, and automate future advisory checks.

HighThe free Render database can expire and has no managed backups

Original findingRender’s free PostgreSQL databases expire after 30 days and do not include recovery. Real trial data could become unavailable or be deleted.

Original repair directionUse a paid database for the real trial or run and verify an external backup process. Rehearse a restore before recruiting.

HighThe “15/15” credit test gives false confidence

Original findingThe script manually simulates simplified balance changes instead of calling the real web routes. It passes while those real routes double-charge users.

Original repair directionReplace it with route-level tests covering signup, holds, acceptance, cancellation, timeout, completion, disputes, repeat sessions, and concurrency.

MediumThe product tells users conflicting stories about credit prices

Original findingThe homepage and marketplace repeatedly say 30 minutes equals one credit, while backend listings can cost up to four credits. Some screens always display “1 credit” regardless of the real charge.

Original repair directionFor the first trial, use one flat credit per 30 minutes everywhere. Remove variable pricing until research proves it is needed.

Original repair directionHide all paid-plan claims during the trial. Do not activate payments until pricing, consumer disclosures, refunds, taxes, and a real provider are ready.

MediumPrices and starter credits disagree across the code and plans

Original findingThe homepage, business plan, environment defaults, and email copy name different prices and different starter-credit amounts.

Original repair directionCreate one source of truth for product configuration and generate all visible copy from it.

MediumThe recurring-session controls do nothing

Original repair directionAdd a single session-details page where both parties see time, place/link, status, cancellation action, safety guidance, and support access.

Implementation path used

The seven-phase program and its current boundary

The repository work followed this order. Phases 1–4 and 6 now have substantial local evidence; Phase 5 is locally exercised but not proven in staging, and the real Phase 7 rehearsal remains incomplete.

Implemented trial contract: one configurable creative vertical, 10–20 invited and manually vetted NYU participants, one credit per 30-minute session, no payments, no request-board claiming, no referral rewards, no proof-video rewards, and no self-service ambassadors.

01

Freeze dangerous features and build a real test harness

First, stop the app from creating new harm while preserving the current experience for diagnosis.

  • Disable bonus-credit, ambassador, top-up, request-claim, recurring-session, and fake meeting-link behavior.
  • Write failing tests that reproduce every confirmed bug from this report.
  • Test through real HTTP routes with CSRF and authorization—not simplified copies of the code.
  • Add CI so a known bug cannot quietly return.
Current evidence: unsafe routes are contained, the obsolete simulator is removed, CI is defined, and 62 warning-strict local tests pass.
02

Rebuild credits and session settlement around strict rules

The credit ledger is the product’s trust core. Nothing else should launch until it is mathematically dependable.

  • Use one service for holds, refunds, payouts, bonuses, and reversals.
  • Link every transaction to a unique session or reward event.
  • Add database constraints, row locks, idempotency keys, and reconciliation.
  • Define and enforce a session state machine and cancellation policy.
  • Run simultaneous booking, claiming, completion, and cancellation tests on PostgreSQL.
Current evidence: local lifecycle, repeat, malformed-source, and reconciliation tests pass, along with three guarded competing-action cases on disposable PostgreSQL 16.14.
03

Make identity, login, email, and authorization real

“Student-only” must be enforced by the server, not merely displayed as a badge.

  • Add strict email validation and a working transactional-email provider.
  • Gate product actions behind successful verification.
  • Secure verification and reset tokens, trusted hosts, session revocation, and rate limits.
  • Separate user, ambassador, moderator, and administrator privileges.
  • Remove token and personal-data leakage from logs.
Current evidence: unverified and unauthorized route matrices pass; shared Redis and trusted-proxy behavior pass locally. Real inbox/provider and deployed proxy/NAT evidence remain external.
04

Build the minimum safe session experience

A successful match still fails if students cannot agree on when and where to meet or get help when something goes wrong.

  • Create a detailed session page with timezone-aware schedule, public place or valid video link, and clear status.
  • Add request, acceptance, reminder, cancellation, completion, and dispute notifications.
  • Add reporting, blocking, no-show, dispute, suspension, and refund tools.
  • Enforce the trial’s allowed skill categories and high-risk-topic ban.
  • Create a moderator queue and immutable action log.
Current evidence: automated two-user and moderator component drills pass, including no-show, dismissal, refund, reversal, suspension, and repeat resolution. Human rehearsal remains BLOCKED.
05

Make data, deployment, and operations recoverable

A trial is not safe if a deployment can erase data, fail silently, or leave the founder unable to recover.

  • Add the PostgreSQL driver and versioned migrations.
  • Create staging and production with separate secrets, databases, and email configuration.
  • Add database-aware readiness checks, logs, error monitoring, uptime alerts, and scheduled jobs.
  • Use a backed-up database and rehearse both restore and rollback.
  • Validate required production settings and refuse unsafe startup.
Current evidence: production-shaped PostgreSQL/Redis exact-head readiness, guarded jobs, and a synthetic local logical restore pass. Real SMTP/staging, deployed proxy/NAT, alerts, and provider recovery remain NOT TESTED/BLOCKED.
06

Align every screen with the real product

High fidelity means the interface tells the truth and every visible control works.

  • Use one credit price, one starter-credit amount, one pilot vertical, and one set of public claims.
  • Remove paid plans and unfinished features from trial-facing pages.
  • Fix accessibility semantics, keyboard use, focus, contrast, and reduced motion.
  • Optimize images and define mobile performance budgets.
  • Verify the entire journey at 375px, 500px, and desktop with screenshots and browser checks.
Current evidence: unsupported controls are removed; isolated Chrome passes public-route truthfulness, 375/500/768/1440 rendering, keyboard/focus, 200% reflow, reduced motion, accessibility-tree naming, strict same-origin CSP, screenshots, and corrected AA contrast. Official DevTools/Core Web Vitals tracing remains unavailable and is not claimed.

Plain-English glossary

Technical words used in this report

Ledger

The permanent list of every credit added or removed. A student’s displayed balance should always equal the total of this list.

Idempotent

Safe to repeat. For example, clicking “refund” twice should still produce only one refund.

Race condition

A bug caused by two actions happening nearly simultaneously, such as two teachers claiming the same request before either sees the other.

CSRF

Protection that stops another website from secretly making a logged-in user perform an action on Relay.

XSS

A security problem where attacker-controlled text or links cause script code to run inside another user’s browser.

Content Security Policy

Browser rules that control which scripts, images, fonts, and network locations a page is allowed to use.

Migration

A controlled, versioned change to the database structure that preserves existing data while the application evolves.

Staging

A private production-like copy of the app used to test releases safely before real users receive them.

Reconciliation

Checking that balances, transactions, session states, and expected totals all agree.

Regression test

An automated test that proves a known bug is fixed and prevents the same bug from returning later.
